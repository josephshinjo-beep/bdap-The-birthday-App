Plan

Build in small, demo-able milestones

Each milestone ends with something you can open on your phone and try with real classmates. We don't move on until you've approved the one before.

M0

Setup

~2–3 days

Approve this design, then set up the project skeleton.

  • Repo structure, Next.js app, Supabase project, deploy a “hello” page to Vercel
  • Colours, fonts and buttons from this prototype turned into reusable components
  • Google sign-in through Supabase Auth, then a one-time profile step (name, username, DOB)
  • PWA shell: installable app, service worker, push permission prompt
  • Styling kept in one theme file so the new look you give later is a quick swap

Done when: a live URL shows the real home page.

M1

Rooms & enrolment

~1–1.5 weeks
  • Interactive home page with “How it works”
  • Moderator: create room → gets a 6-character code
  • Student: enter code → room preview → name, username, DOB → request sent
  • Moderator dashboard: let in / decline requests, live count
  • Waiting screen that switches to the room by itself once approved (realtime)
  • Room page: member list and upcoming birthdays (day + month only)
  • Edit room, make a new code, add a co-moderator

Done when: you create a room, 3 friends join, you approve 2 and decline 1, and the approved ones land in the room.

M2

Secret reminders & UPI

~1–1.5 weeks
  • Daily scheduled job finds birthdays tomorrow and today (India time)
  • Creates a “celebration” per birthday, visible to everyone in the room except the birthday person
  • Sends notifications: in-app feed + Web Push to the installed PWA / browser
  • Multiple UPI IDs per room with automatic rotation after a set number of payers (see Architecture)
  • Moderator picks the amount mode: fixed, suggested, or any amount
  • Surprise page: tap-to-unwrap gift → scratch card → UPI QR, UPI ID, amount, “Pay with UPI app” button
  • “I've chipped in” tick. Members see the pool total; moderator and co-moderator also see who paid. The birthday person sees none of it
  • Moderator's own birthday is handed to the co-moderator automatically

Done when: with a test birthday set to tomorrow, everyone but that person gets the 6 PM reminder and can unwrap the QR.

Architecture

One web app, one database, one daily job

The stack is chosen to be free to run for a class, quick to build, and safe by default about who sees what.

PartChoiceWhy
Web appNext.js (React) + TailwindPages and server code in one project; works great on phones
Database & loginSupabase (Postgres, Auth, Realtime, Storage)Free tier; row-level security hides celebrations from the birthday person at the database level
HostingVercel, with your domain's DNS kept on CloudflareBest Next.js support, zero adapter work. Cloudflare just points bdap.yourdomain at Vercel
Scheduled jobSupabase pg_cron + pg_net calling /api/cron/reminders with a secretFires at exact times (6:00 PM, 7:30 AM IST). Vercel's free cron only promises “within the hour”
NotificationsIn-app feed (Supabase Realtime) + Web Push (VAPID) via a service worker in the PWAFree. Works on Android Chrome, desktop, and iPhone once the PWA is added to the home screen (iOS 16.4+)
UPI QRGenerated from upi://pay?pa=…&pn=…&am=50&tn=Riya bdaySame link opens GPay/PhonePe/Paytm directly on phones

The secrecy rule

The database itself refuses to show a celebration to its birthday person: a row-level security policy allows reading celebrations and contributions only if you're an approved member of the room and birthday_user_id ≠ you. Even a bug in the app can't leak the surprise. The notification job filters the same way.

When the moderator has the birthday, the QR switches to the co-moderator's UPI for that celebration, and the moderator is locked out of it like anyone else.

UPI rotation

The moderator adds 2–3 UPI IDs and links each to the member who owns it. When someone opens the surprise, the app assigns them a UPI ID and remembers it, so they always see the same QR:

  • Skip any UPI ID owned by the birthday person (covers the moderator's own birthday)
  • Use the first remaining ID until it has payers_per_upi people assigned (moderator sets this, default 20), then move to the next
  • If every ID is full, keep filling the one with the fewest, and alert the moderator to add another

A note on the 20 limit: the well-known NPCI limit of 20 UPI transfers a day applies to the sender's account, and I'm not sure there's a fixed cap on receiving. Since the cap is a setting the moderator controls, the app works either way.

One honest limit about UPI

Without a payment gateway (Razorpay etc., which needs a registered business), the app can't see whether someone actually paid. “I've chipped in” is self-reported; the moderator can cross-check against their UPI app. That's fine for a class project, and we can add a gateway later if needed.

Agreed

Decisions

1 Google login via Supabase · 2 college first, no birth year shown · 3 in-app + Web Push, built as a PWA · 4 multiple UPI IDs with rotation, birthday person's ID skipped · 5 moderator sets amount mode · 6 multiple rooms per student · 7 pool total for members, who-paid for admins · 8 Next.js + Supabase, hosted on Vercel with Cloudflare DNS · 9 new look comes later; current style is a placeholder.

Original questions

  1. How should people log in?Username alone can't stop someone pretending to be you.

    My pick: Google sign-in, with email one-time code as a backup. Students then fill name, username and DOB once.

  2. Who are the users: school or college?Under-18s (especially under-13s) need extra care with names and birthdays.

    My pick: design for college first; never show the birth year anywhere.

  3. Which notifications do you want in M2?Browser push needs permission and works best if the site is “installed” on the phone.

    My pick: in-app + browser push now, email as a fallback, WhatsApp later.

  4. Where does the money go?The prototype sends it to the moderator's UPI. Another option: a chosen “treasurer” per celebration.

    My pick: moderator's UPI by default, co-moderator's when it's the moderator's birthday.

  5. Fixed amount or any amount?

    My pick: moderator sets a suggested amount (₹50); people can change it.

  6. Can one student be in more than one room?e.g. class room + hostel room + club.

    My pick: yes, it costs little to support now and is hard to add later.

  7. Should the room show the pool total to members?

    My pick: show “18 of 40 chipped in”, but only the moderator sees who exactly.

  8. Do you have a preferred tech stack, or what do you already know?If you want to learn while building, I'll pick something you can maintain.

    My pick: Next.js + Supabase + Vercel, all free tiers.

  9. Does this look and feel right?Colours, the playful tone, the gift + scratch-card reveal, button placement.

    Tell me: anything you'd change on any screen.
